# ADR-013: Metodología de benchmarks comparables

**Estado**: aceptada (2026-11-11)
**Contexto**: Hito 8 / TASK-801. Necesitamos medir Zen frente a C, C++ y Rust sin convertir el laboratorio en publicidad.

## Problema

Un benchmark puede ser injusto por muchas vías: distinto algoritmo, distinta entrada, distinto nivel de optimización, distinto trabajo de asignación, o medición contaminada por el planificador y la frecuencia del host. Además, el bootstrap actual compila Zen a C11 y usa `cc -O2`: Zen y C comparten backend, así que cualquier comparación debe declararlo.

## Alternativas evaluadas

1. **Tiempo de pared de una sola ejecución**: simple, pero en este host se observaron muestras bimodales (~2x) por desalojos del planificador con el proceso fijado a una CPU. Inaceptable como métrica primaria.
2. **Tiempo de CPU del hijo (`getrusage`)**: mide el tiempo de CPU consumido (no ciclos ni instrucciones), inmune a desalojos del planificador aunque no a cambios de frecuencia ni a contención SMT; no incluye esperas de E/S. Es la métrica elegida como primaria.
3. **Ciclos de CPU vía `perf`**: más preciso, pero `perf` no está disponible y requeriría permisos.
4. **Benchmark de recursión (fib)**: descartado de la comparación principal. **Hipótesis no verificada** (no se conservaron fuentes ni JSON de la prueba exploratoria): el inlining recursivo puede variar entre lenguaje y compilador (GCC para C, LLVM para Rust) y Zen no permite solicitar `noinline`, de modo que la comparación mediría heurísticas del compilador y no el lenguaje. Se sustituyó por `collatz`, con ramas y sin recursión, que no depende de esa heurística.
5. **Comparar con Zig y clang**: imposibles en este host (no instalados). Se declaran «no disponible», sin estimaciones; el arnés sondea ambos.
6. **Incluir `mem`/`sort` con `malloc`**: se mantiene, con `malloc`/`free` de libc en los cuatro lenguajes (Rust vía `std::alloc` sin zero-init) para igualar el trabajo de asignación.

## Decisión

- Cada benchmark existe en `zen/`, `c/`, `cpp/` y `rust/` con el **mismo algoritmo y datos**; imprime un checksum determinista.
- El arnés compila, ejecuta y **verifica que los checksums coinciden antes de medir**; una discrepancia aborta.
- Métrica primaria: **tiempo de CPU del proceso hijo**, medido con `getrusage(RUSAGE_CHILDREN)` alrededor de cada ejecución.
- Las ejecuciones se **intercalan por lenguaje** dentro de cada repetición para repartir episodios lentos del host.
- Se reportan mediana, mínimo, media, desviación y muestras crudas (todas presentes en el JSON); el tiempo de pared se conserva como referencia.
- Cada ejecución se fija a una CPU (`sched_setaffinity`), con degradación a ejecución sin fijar si el entorno lo impide.
- Se reportan también tamaño del binario y tiempo de compilación de cada implementación.
- No se usan hints de inline específicos de un lenguaje; la implementación Rust de `sort` los retiró para no introducir una asimetría.
- El JSON incluye host, versiones de compilador, configuración y carga media inicial.

## Consecuencias

- Zen y C comparten `cc -O2`: diferencias Zen↔C miden el código generado y el runtime del lenguaje, no un backend propio.
- Los resultados no son un ranking absoluto de lenguajes ni generalizan a otro hardware.
- Cualquier afirmación de rendimiento futura deberá repetir esta metodología, adjuntar el JSON de la ejecución y declarar la variabilidad entre ejecuciones; diferencias de pocos puntos porcentuales no se consideran señal en este host.
- Condición de revisión: si se incorpora un backend propio (LLVM/Cranelift) o `perf`, revisar la métrica primaria y añadir ciclos/instrucciones.
