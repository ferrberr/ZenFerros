# ADR-021: Linter `zen lint` con diagnósticos JSON

**Estado**: aceptada (2026-11-11)
**Contexto**: Fase 9 / TASK-909. El compilador solo emitía diagnósticos de error; editores/CI necesitan avisos y formato machine-readable.

## Decisión
- Nuevo subcomando `zen lint [--json] [--deny-warnings] [--target host|freestanding] <archivo>`.
- Reglas iniciales sin falsos positivos: `unused-variable` (let nunca leído; prefijo `_` ignorado; asignación/escritura de campo/índice **no** cuenta como lectura; `+=` sí), `unused-parameter` (parámetro nunca leído; `_` ignorado; extern sin cuerpo no se analiza), `unused-function` (privada definida sin llamada en código alcanzable; `pub`/`extern`/`main` no), `unreachable-code` (sentencias directas tras `return` en el mismo bloque; no desciende para evitar cascadas).
- Salida humana `archivo:linea:columna: severity[code]: mensaje`; `--json` emite una lista de objetos con `severity`, `code`, `message`, `file`, `line`, `column`, `span_start`, `span_end` (escape manual, sin dependencias nuevas).
- Exit codes: 0 sin errores (warnings permitidos), 1 errores (de lint o compilación), 2 con `--deny-warnings` si hay warnings (los errores mandan con 1).
- El linter ejecuta primero la validación completa del compilador; si falla, reporta `error[compile-error]` con el mismo esquema. No exige `fn main` en host para permitir lint de módulos/ejemplos freestanding.

## Alternativas rechazadas
- Reutilizar `codespan` para JSON: acopla formato de editor y no es estable para CI.
- Linter basado en texto: falsos positivos con scopes/structs.
- Análisis de alcanzabilidad completo: fuera de alcance; se documenta como falso negativo (llamada desde código muerto mantiene viva la función).

## Consecuencias
- `zen lint --json` es consumible por editores/CI; 18 tests CLI + 2 unitarios.
- Límites: sin alcanzabilidad/CFG, sin lint de estilos (nombres, longitud), sin autofix, sin LSP.
- Condición de revisión: al añadir CFG/typechecker completo, ampliar reglas y mantener estabilidad del esquema JSON.
