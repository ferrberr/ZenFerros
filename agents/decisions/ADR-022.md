# ADR-022: Servidor LSP mínimo por stdio sobre el linter

**Estado**: aceptada (2026-11-11)
**Contexto**: Fase 9 / TASK-910. Faltaba integración con editores; el linter ya produce diagnósticos con spans y JSON estable.

## Decisión
- `zen lsp` implementa JSON-RPC 2.0 por stdio con framing `Content-Length: N\r\n\r\n{json}`; parser JSON manual (sin dependencias nuevas), lectura `read_exact` tolerante a frames partidos y flush por mensaje.
- Métodos: `initialize` (textDocumentSync=1 full, positionEncoding utf-16, serverInfo), `initialized`, `didOpen/didChange/didSave/didClose` → `textDocument/publishDiagnostics`, `shutdown`/`exit`. Métodos desconocidos `-32601`; JSON inválido `-32700`; mensaje no-objeto `-32600`; notificaciones desconocidas se ignoran.
- Diagnósticos: `severity` LSP (1 error, 2 warning), `code` del linter, `source: "zen"`, `range` con líneas 0-based y carácter en UTF-16; los errores del compilador llegan como `compile-error` severity 1.
- El servidor mantiene buffers por URI y versiona; no lee archivos (el cliente envía el texto). Sincronización **full**, loop síncrono sin hilos.

## Alternativas rechazadas
- `tower-lsp`/`lsp-server`: dependencias nuevas para un subconjunto pequeño; se prefiere control y reproducibilidad offline.
- LSP con pull diagnostics/CFG: requiere typechecker completo y cancelación; fuera de alcance.
- Leer archivos del disco en `didOpen`: rompe el modelo del editor y duplica la fuente de verdad.

## Consecuencias
- Editores pueden mostrar errores/avisos en vivo con el mismo criterio que `zen lint --json` (12 tests end-to-end + 3 unit).
- Límites: solo push diagnostics y sync full; sin hover/completion/definition/rename/code actions/formatting, cancelación ni concurrencia; `Content-Length` ≤64 MiB; EOF sin `exit` termina 0.
- Condición de revisión: al añadir typechecker/CFG, evaluar diagnostics incrementales y cancelación.
