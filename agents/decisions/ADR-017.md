# ADR-017: Structs nominales mínimos en el subconjunto MVP

**Estado**: aceptada (2026-11-11)
**Contexto**: TASK-214. Tras los arrays, el autohosting necesita agrupar campos con nombre (token, símbolo) sin pasar aún a un sistema completo de tipos.

## Decisión
- `struct Name { field: T, ... }` de nivel superior; campos **escalares** (`u8/u16/u32/i32/i64/u64/bool`); sin genéricos, métodos, anidamiento ni arrays como campo.
- Construcción `Name { field: expr, ... }` con campos exactos y tipos exactos; acceso/escritura `p.x` (escritura solo con `let mut`).
- **Solo variables locales**. Struct como parámetro, retorno, campo de struct, copia/asignación completa, comparación o cast se rechaza con diagnóstico localizado.
- Layout C natural: `typedef struct { ... } __zen_Struct_Name;` antes de las funciones; sin ABI externa de structs.
- Nombres internos derivados del nombre Zen; sin reflexión ni métodos.

## Alternativas rechazadas
- Structs con parámetros/retorno: exige decidir convención de paso, copia y ABI; fuera del MVP.
- Anidamiento/arrays en campos: multiplica layout y chequeos; no necesario todavía.
- Pasar structs como punteros: requiere semántica de préstamo; mejor punteros raw explícitos.

## Consecuencias
- Se pueden modelar tokens/símbolos con nombre en Zen; el AST de arrays sigue siendo válido para nodos homogéneos.
- 14 tests nuevos (71 en total) y `zen run zen/examples/structs.zen`.
- Límites: sin métodos, sin paso entre funciones, sin structs en arrays, sin layout explícito/empaquetado.
- Condición de revisión: al añadir paso de structs o métodos, revisar ABI, copia y tests negativos.
