# ADR-008: Freestanding mínimo x86_64 y ABI C explícita

**Fecha**: 2026-11-11
**Estado**: ACEPTADA (implementación y evidencia TASK-310, revisión TASK-311)
**Responsable**: Orquestador 00
**Dependencias**: ADR-007, TASK-210

## Problema

El Hito 1 produce programas hosted que requieren main/libc. Ferros necesita objetos enlazables sin startup del host, símbolos externos controlados, salida serie mediante helpers de arquitectura y acceso explícito a memoria de dispositivos.

## Decisión

Continuar el backend C de bootstrap. `--target x86_64-unknown-none --emit obj` compila con GCC x86_64 disponible, sin libc y sin enlazado automático. No se instala una nueva toolchain ni se anuncia compilación cruzada general. `--emit c` permite inspeccionar el C validado. `check` acepta el target y no requiere main en freestanding.

En freestanding, `pub fn` exporta un símbolo con el nombre Zen y ABI C System V AMD64. En hosted, `pub` solo expresa visibilidad y conserva nombres internos para evitar interponer símbolos de libc (por ejemplo printf/fwrite). `extern "C" { fn ...; }` importa firmas. Solo escalares y punteros en la frontera ABI; las vistas str permanecen internas. Calls extern, casts entero/puntero y accesos volatile requieren bloque unsafe. La capacidad unsafe reconoce la responsabilidad del autor sobre dirección, alineación, vida y efectos del dispositivo; no afirma que un puntero sea válido.

Se añaden enteros u8/u16/u32, casts enteros explícitos y operadores de bits con semántica definida. Los punteros raw se limitan a enteros de anchura conocida; no hay aritmética de punteros ni referencias con lifetimes. Intrínsecos volatile_load/store permiten MMIO; la entrada/salida por puertos se suministrará mediante un helper de arquitectura C/asm para el primer boot. No se implementa inline asm del lenguaje en esta iteración.

El runtime freestanding usa operaciones enteras y traps nativos; sin stdio/stdlib/string/memcpy ni startup hosted. Las cadenas literales son estáticas y se recorren mediante str_len/str_byte. El trap no desenrolla ni imprime mensajes: el kernel deberá proporcionar manejo de excepciones posteriormente.

## Flags del objeto

C11 y -O0/-O2; -ffreestanding -fno-builtin -fno-stack-protector -fno-pic -fno-pie -fno-common -m64 -mno-red-zone -mgeneral-regs-only -mcmodel=kernel -fno-asynchronous-unwind-tables -fno-unwind-tables -fno-ident -fno-tree-loop-distribute-patterns -ffunction-sections -fdata-sections, con -c. Se desactiva red zone, SIMD y metadatos/unwind para preparar llamadas de kernel; no se prueba interrupciones/SMP todavía. El code model kernel requiere layout enlazado apropiado (rango de direcciones compatible); el script Linux de prueba usa direcciones bajas dentro de ese rango.

## Alternativas y revisión

- Cambiar inmediatamente a LLVM/Cranelift: posible pero no necesario para demostrar objetos freestanding y ABI, añade dependencias/integración sin cerrar todavía el boot.
- Implementar todo el lenguaje de sistemas antes de emitir objetos: amplía demasiado la iteración. Structs/layout, arrays y más intrínsecos se implementarán cuando haya un consumidor verificable en Ferros.
- Ejecutar código privilegiado en host: fuera del plan. La prueba solo usa funciones de usuario y syscalls desde un adaptador Linux; el boot real tendrá lugar en QEMU en Hito 3.

Revisar esta decisión si GCC inserta dependencias implícitas, si el código de kernel requiere un target/code model diferente o si los benchmarks justifican otro backend.

## Evidencia necesaria

Objeto ELF64 REL con símbolos exportados/importados previstos; pure object sin undefined; demo enlazada sin bibliotecas con _start y sin INTERP/NEEDED; resultado real comprobado. Harness C verifica enteros, ABI, strings y volatile sobre buffers válidos. Negativos verifican unsafe/tipos y traps. Regresión completa hosted y revisión independiente.
